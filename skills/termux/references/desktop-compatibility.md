### 小米窗口外观与合成补充验证

同日维护时，原 `Tablet-Touch` 主题的侧边素材宽 12 像素；普通 Greybird 在高密度屏幕上需检查标题裁切，可选系统自带 `Greybird-dark-accessibility`。没有替换驱动、降低原生分辨率或修改应用绘制代码。

固定 WebGL 负载仍为本页的画布、视口、DPR 和预热/采样方法，各三轮：无合成中位约 92；Xfwm/XPresent 约 46，关闭合成同步约 45；Xfwm 加载直接 KGSL 后的 GLX 路径约 59。Picom 12.5/直接 KGSL 约 74，但后续窗口管理器重入出现全屏黑画面，正常停止 Picom 后恢复，因此该路径未通过稳定性验收、未设为默认。实际 GPU 设备与绘制成功不替代屏幕可见性。

最终保留 Greybird 的深色大标题栏变体和原有无合成 GPU 通路；回退后同负载三轮中位约 90，窗口最大化/还原、调整大小及原生触屏拖动复测通过。实验合成器与本次新增依赖、启动脚本均撤除。拖动时背景重绘仍是已知限制，不将功能可用写成流畅度问题已完全解决。

在自建窗口、固定移动轨迹的对比中，无合成每轮约 196–200 次背景重绘，启用合成后为 0。合成配置同时调整了主题并停用了旧底栏重定向辅助，属于整套配置对比；不能把 CPU/呈现差异归因于单一开关。移动期间高频 SurfaceFlinger 时间戳不证明图像内容正确，不引用黑屏方案的计数作为可用 FPS。保留浏览器性能与采用有开销的合成之间，应向用户说明实际取舍。

### Y900 鼠标与面板刷新率

本次连接蓝牙鼠标，输入模式保留用户当前的 Trackpad。Xrandr 仍显示约 120Hz，但 Android 活动模式实际为 30～60Hz。临时设置 `min_refresh_rate=120.0` 后回读确为 120Hz；仅请求临时 preferred display mode 没有提高实际频率。首次两分钟试验用户未及测试，已自动恢复；重新提供五分钟试验后，用户反馈 Android 很顺，Xfce 仍稍差。用户最终选择原来的自动刷新率，最低频率恢复缺省，保留 `peak_refresh_rate=120.0`，不持久化全局 120Hz；本次续航未测试。

只统计指定鼠标移动包的 EventHub 时间，共 2567 个报告，连续活动间隔中位约 7.511ms、P95 15.002ms；其中 2303 个间隔在 4～9ms，长间隔含停手/切换窗口，未归类为无线丢包。结合 Android 顺畅的反馈，尚无证据认定鼠标硬件故障。标准捕获模式实读为 RELATIVE 后，用户感到稍顺，但指出边栏难以瞄准，进一步将问题描述为微操/加速；不能把该轮写成鼠标全部通过。

进一步核对 density=2.5、捕获倍率 100 及 X11 鼠标反馈 2∶1/threshold 4；用捕获倍率 40 与该鼠标 1∶1 反馈作为线性参照，保留阈值、触屏模式和自动刷新率。五分钟试验先按约定自动回退，用户随后确认“微操正常，保留此设置”。已重新应用 capture=true、倍率 40，并通过 Xfce 标准 `/Lorie_mouse/Acceleration` 的 double 1.0 持久化；实际反馈回读为 1∶1/threshold 4，原始属性不存在的状态及设置已备份。用户确认的边栏精细定位和文字选区通过；其他设备倍率、触控板完整回归及 Android 重启后实测不由此推定。

随后用户说“拖不动”，澄清为整体移动太慢，未报告左键拖拽失效。40、60 均被反馈偏慢；100 仍偏慢且低速难以精确命中侧栏。停止继续调参，固定 capture=true、倍率 100、Xfce 1∶1，改用两端只读事件对照。原生密度参照与跨屏移动舒适度是两个验收项，不能把微操通过写成整体速度也合适。

有效记录包含 2698 个 Android 相对移动报告和 1305 个 XInput2 更新，典型非零报告间隔分别约 7.498ms、17ms，最小非零轴增量分别为 1 原始计数、2.5 相对坐标单位。1305 条更新全部能按 2.5 倍增益对应原始报告的连续合并：178 批各 1 条、867 批各 2 条、254 批各 3 条、6 批各 4 条，恰好覆盖全部 2698 条；处理后位移与 XInput2 原始位移完全一致。该记录支持固定增益及合批，而非随机丢失净位移；报告数、时间间隔均不是硬件轮询率、屏幕 FPS 或完整视觉延迟。鼠标节点消失、无有效运动的记录均排除。

交付清理发现，主机采样退出后有 3 个设备端 getevent 孤儿读取器因设备断开而空转，造成额外 CPU 负载。逐项核对 UID、精确参数和启动时间，与本轮 3 次探针启动记录匹配后已回收，零残留检查通过。这是诊断回收遗漏，相关时序只能作为带诊断负载的观察，不能据此认定无负载转发上限或纯粹由显示节拍造成；逐批净位移匹配结论保持有效。旧私有采样入口已禁用，后续采样须使用设备端身份监督与退出回收。

经用户同意，只关闭 pointerCapture，转回 Android 原生指针位置转发，保留倍率 100、Xfce 1∶1、Trackpad 触屏模式、GPU 和自动刷新率。用户确认速度与微操均改善，要求保留原生路径；最终 pointerCapture=false，倍率 100 在该路径不参与位移计算。额外 Core 事件采样未在连接等待期间取得有效记录，未据此声称采样率提高或最小像素步长下降。Code 默认侧栏命中区宽度为 4 逻辑像素、悬停高亮延迟 300ms，本次没有修改这些设置；具体实现见 [VS Code 1.146 的 Sash 源码](https://github.com/microsoft/vscode/blob/1.146.0/src/vs/base/browser/ui/sash/sash.ts)。本次没有改输入源码、预加载库或驱动。

### Y900 Chromium 浮动窗口外缘

同轮查看用户指出的 Chromium 外框，浮动窗的 `_NET_FRAME_EXTENTS` 为四边 0，`_GTK_FRAME_EXTENTS` 为四边 10，Xfwm 合成关闭。屏幕可见深色外缘来自客户端装饰；未观察到额外 Xfce 框架。标准最大化后可见外缘消失、标签栏仍为单行；随后恢复原浮动窗口的位置和尺寸，回读一致。该操作没有证明浮动外缘已被永久去除，也没有更改浏览器样式、GPU 或桌面合成；不得为此重新加上用户已否决的独立系统标题栏。

2026-11-16 后续核对：窗口 depth24、实际 compositor owner 为空，Chromium 157 对应实现采用实色客户端装饰，不应将 GTK extents=10 直接称为 10 像素透明阴影。官方外观页显示 GTK，点击 **Use Classic** 后 `extensions.theme.system_theme` 从 1 变为 0，多层粗边框消失，仍有标准窄边缘/缩放区域；用户确认合适并要求保留。单行标签栏和原窗口几何保留，关闭仅本轮新增的设置标签并返回原 GPU 页；GPU、输入、自动刷新和合成配置未改。该主题选择不自动推广给小米或其他设备，操作方法见 [窗口边框参考](desktop-display-input.md#窗口边框拖动重绘与合成)。

### Y900 整窗移动的呈现短样本

同日，日常 Chromium 的真实 GPU 页面仍报告硬件 Canvas/Compositing/Rasterization/WebGL/WebGPU，GL_RENDERER 为 Adreno 830 / ANGLE GLES / Zink / Turnip；Code 有 GLES、独立驱动映射及 KGSL FD 证据，但同实例 `--status` 输出为空，未取得新的 GPUFeatureStatus。两者的硬件证据强度不同；原有终端 DOM 和 Chromium mailbox 保留，不据此推定整体软件回退。

自动刷新保留；本次快照为静置 30Hz、运动早期查询 30Hz、结束后 60Hz，Xrandr 仍约 120Hz。无真实输入的 EWMH 短平移约 2 秒，120 个请求、121 次 ConfigureNotify 含恢复，原几何回读一致。严格裁剪运动起止后，SurfaceView BLAST 历史的末约 1 秒有 61 个有效 actualPresent 时间戳，间隔约 16.67ms；这不是完整运动轨迹、实鼠 FPS、输入延迟或像素正确性验证。

完整运动期的 0.5 秒 CPU 区间，Xserver 进程约单核 58～60%（其中 LorieRenderer 40～44%、主线程未记录到增量）、PRoot 30～34%、底栏辅助 22～24%；CPU 随移动增加，但不能据此认定瓶颈或辅助致因，之前辅助运行/停止的重绘对照仍保留。整窗拖影尚未定位或修复，也未在本轮开启合成、固定 120Hz 或升级驱动。该样本支持继续区分 root 重绘/同步与最终呈现，不支持把短尾均匀呈现写成全程画面无残影。
